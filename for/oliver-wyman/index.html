  2. Where agent value gets lost: after it works

    An agent can pass every test and still never reach the P&L. The Reality Check puts numbers on it: only 8% of workplace AI users say their company has a company-wide standard for what happens to the time AI saves, and 54% say each person decides, or nobody does. For this role, that moves two decisions to the start of the work instead of the end: the baseline, measured before anything is built, and what the saved time becomes, agreed with the client's sponsor before go-live. Without both, "measure realised value after deployment", as your posting puts it, has nothing to measure against.

  3. One engagement, worked through: a bank's KYC review

    At GMNG I led our KYC verification flow, from design and implementation to testing, so I'll use KYC review as the example. Discovery first: sit with the reviewers, follow live cases, and map every step, exception and decision, timing each one. That timing is the baseline. Then sort the steps three ways, starting from what the bank's verification provider already does, since some checks may sit there already. Rules stay rules: format checks, expiry dates and duplicate checks need simple automation, not an agent. An agent goes where judgement on messy input sits today: reading a document that doesn't match the form, requesting what's missing in messages Compliance has approved, and drafting the case summary with every statement linked to its document. I'd start with one agent and split it into separate roles only where the tests show it mixing up jobs. People keep the decisions: a reviewer approves or rejects every case, and high-risk cases go straight to a senior reviewer. The agent gets only the access its job needs, read-only on customer records and write access only to the case file. When a check fails or a document can't be read, it stops, records what it did and didn't do, and hands the case back to the queue. Cost is part of the design from the start: at GMNG I cut what we paid our verification provider by reusing data across its separately billed API calls, so an agent that runs a paid check twice is a defect. With the AI Product Engineers I'd agree what's feasible on the bank's systems, and turn each constraint into a choice the sponsor can make, such as a cheaper overnight check or a faster paid one. Before engineers build anything, I'd prototype the flow myself on synthetic customer files, in Claude Code or the agent platform the client already uses, and refine its instructions and the knowledge it draws on against realistic cases with the reviewers.

  4. Acceptance before anyone relies on it

    A test set built with the reviewers from sanitised past cases, cleared with the bank's data owners, covering what your posting lists. Successful outcomes: clean cases, summarised correctly. Edge cases: an expired document, a name spelled differently on two documents, a blurred scan. Incorrect outputs: a summary that says a check passed when it didn't fails the whole run, whatever the rest scores. Failed actions: the provider times out, or an upload breaks mid-case, and the case still lands in the queue. Escalation: a high-risk flag reaches a person every time. I'd own business acceptance and bring in security, risk and legal for their own sign-off, with the decision boundaries written down before the pilot: what data the agent may see, what it may change, and what it may never decide. Every case a reviewer corrects during the pilot becomes a new test, so the set grows from real failures. I've worked this way before. At MR Neo I audited all 60+ pages of the platform, logging 588 bugs and UX issues, then recorded four to five hours of myself testing and thinking aloud and turned that into Claude skills, folding in existing skills to make them better at finding bugs. On Lará, the AI hotel platform I'm prototyping, each of seven build phases ended with a security attack-and-harden pass, and it has 260 automatic database security tests.

  5. What value means, agreed before the build

    The same measures, taken before the build and again after go-live. Productivity: minutes per case and cases per reviewer per day. Quality: errors caught at review, cases reopened, and how often reviewers override the agent's draft. Adoption: the share of cases where reviewers start from the draft instead of redoing it, read weekly. A falling override rate only means trust if errors caught stay steady, because a reviewer who stops checking also stops overriding. Cost: cost per case, including every paid provider call. And one decision written down with the sponsor before go-live: what the saved time becomes, whether faster onboarding for customers, more cases for the same team, or senior reviewers moved onto high-risk cases. Together that baseline and decision are the business case. Targets come from the baseline, set with that sponsor, not promised up front, and after go-live the backlog is ordered by the same evidence. Where the numbers show the agent isn't paying for itself on a step, that step goes back to simple automation or to a person.

  6. Built so the client's team can run it

    Reviewers should supervise the agent, not just receive its output. Every step it took is shown with its source, a reviewer can correct a field and the correction is kept, and a case can be taken back from the agent at any point without losing work. I'd test that screen with reviewers before go-live, the way I redesigned GMNG's first-time experience after talking to users about their pain points, which lifted user satisfaction 20%. Handover is part of the product: the client's team gets the blueprint, the test set and a short runbook for adding a case type or changing an instruction and rerunning the tests, so they can extend it without us. MR Neo's team already uses and improves the testing skills I built, and at Sovena I handed my consumer research over as a NotebookLM base the team could keep querying. What repeats goes back to the practice, such as the discovery template, the test-set pattern and the value sheet, so the next engagement starts from them.
